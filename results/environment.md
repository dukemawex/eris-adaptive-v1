# Environment and toolchain

Measured in a Claude Code cloud container (4 vCPU, 15 GiB RAM, no swap), not GitHub Codespaces.

## Simulator

- `NyxFoundation/eris-agent-simulator` @ `3bee7ec` (main, 2026-10-04), cloned next to this repo.
- Node v22.22.0, npm 10.9.4, Python 3.11.15 (`sdk-py` installed into `.venv`).
- Steps followed are the repository's own: `npm install`, `forge build`, `deployer/` `npm install`,
  `forge build`, `scripts/setup-vendors.sh`, `npm run anvil` + `npm run deploy -- --keep-fresh`
  (MANAGE_ANVIL=false, as `.github/workflows/deploy-backtest.yml` does), `gen:local-constants`,
  `gen:state-dump`, then `npm run backtest ... --agent-sandbox process` (Docker images were not built;
  the official regimes default to docker sandboxes with the rules' 2 vCPU / 4 GiB caps, so CPU and
  memory caps were not exercised).
- Nothing in the simulator was modified. Additions only: agent directories under
  `example/agents/eris-adaptive-*`, tests under `test/eris-adaptive-*`, rosters under
  `config/agents/`. `sdk/src/constants.local.ts` was regenerated by the documented
  `gen:local-constants` (addresses of the local deploy); restore it before bundling a submission.

## Canonical toolchain vs what was installed

The repository has no devcontainer and no pinned toolchain lockfile. CI installs Foundry with
`foundry-rs/foundry-toolchain@v1` (`version: stable`, GitHub release assets); forge (svm) and Hardhat
(GMX: solc 0.8.29, Aave: prebuilt artifacts, Liquity: 0.6.11 via forge) download solc from
`binaries.soliditylang.org`.

**Blocker:** this container's egress policy returns 403 for GitHub release asset hosts and for
`binaries.soliditylang.org`, so the canonical installers cannot run.

**Clean fix (recommended):** allow those hosts in the environment's network settings (Edit
environment → Network access → Custom, add `binaries.soliditylang.org`,
`objects.githubusercontent.com`, `release-assets.githubusercontent.com`, keeping the default package
manager list; https://code.claude.com/docs/en/cloud-environments#network-access). For Codespaces the
equivalent is a `.devcontainer` that runs `foundryup` (or the foundry-toolchain image) with those
hosts reachable.

**What was used meanwhile (official artifacts, same compiler versions):**

- Foundry 1.7.1 from the npm packages foundry-rs publishes from its release pipeline
  (`@foundry-rs/forge`, `@foundry-rs/anvil`, `@foundry-rs/cast`).
- solc from npm `solc` (the official `soljson` emscripten build of the *same release commit*:
  0.8.20+commit.a1b79de6, 0.8.29+commit.ab55807c, 0.8.10+commit.fc410830, 0.6.11+commit.5ef660b1),
  behind a small native-CLI shim (`scripts/solc-shim.cjs`: `--version` and `--standard-json`),
  registered in `~/.svm` for forge and in Hardhat's compiler cache.
- GMX's 430-file output is too large for solcjs to serialise in one call ("Error writing output
  JSON"), so the shim splits `outputSelection` into chunks compiled in parallel and merges them.
  `outputSelection` is not part of the metadata hash and does not change codegen.

**Equivalence check performed:** for `ExchangeRouter`, `DataStore` and `OrderUtils` (GMX), the
creation and runtime bytecode from a separate compile of only those files was compared with the
merged chunked build used for the deploy: identical (3/3). A comparison against a native solc binary
was not possible (blocked host). The deploy completed and every venue passed the runtime preflight.

## Operational limits found

- Each backtest anvil holds ~1.3 GB RAM and spills history to `~/.foundry/anvil/tmp` (≈1 GB at start,
  growing). Nine concurrent runs exhausted RAM (load average 70, runs discarded); the disk allowance
  also filled from spill left by killed anvils. Runs are now 4 concurrent, one 5-scenario matrix per
  anvil, with exited anvils' spill removed between matrices (`scripts/run-worker.sh`).
